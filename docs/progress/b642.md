## How conflicts worked before (read from code at `c3302f6`)

- The 3-way merge runs **only on the client**, in `SyncClient.pull()`
  (`apps/web/src/sync/sync-client.ts#resolveTextConflicts`), never on the server.
- Trigger: a pulled `block.text` op whose block still has an unacknowledged local `block.text` in
  `pending_op`. Base = `pending_op.base`, the block's content captured in `applyLocal` just before
  the local edit.
- `packages/core/src/sync/text-merge.ts#merge3`: word/whitespace-token diff3. Clean when the edits
  touch disjoint spans (or are identical) → a new `block.text` with the merged text, newer HLC.
  Overlapping hunks → LWW keeps the newer text and the client adds
  `block.prop conflict_copy = <loser>` on the same block — the chip the owner saw.
- The owner's case (both replaced the whole text) is a true conflict.
- Both devices can resolve the same conflict (e.g. a push whose response was lost). Harmless for a
  keyed property, not for a new block — which is why the server mints it.

## Decision — ADR 027 (`docs/adr/027-conflict-copy-as-sibling-block.md`)

Clients unchanged (still push `conflict_copy`). `serverApplyOps`, for `sync` pushes, turns each
report into a server-authored `block.create` right after the winner (`sync-conflict:: true`) plus a
`conflict_copy = null` clear. Block id = 70 bits of sha256(winner id, NUL, text) → a second report
of the same conflict is a no-op; a deleted copy is not resurrected. No migration of existing
`conflict_copy::` values (a block that conflicts again carries its old value along). UI renders
`sync-conflict` as a small "sync conflict" badge. ADR 003's Consequences point to ADR 027; wiki
`Sync.md` updated.
