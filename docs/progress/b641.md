## Decision: maintain the index on the replica, with the server's code

Alternatives considered:

1. **Keep references server-only, nicer offline message** — rejected: the owner explicitly wants
   them to work offline, and the replica holds the whole graph.
2. **Compute references on the fly from block text (no index)** — rejected: `path_ref` semantics
   (ancestor refs, aliases, `tags::`, the derived `#Task`, journal-title keys) would be a second
   implementation that drifts from the server's; and a scan of 18.6k blocks per read.
3. **Same index, same code (chosen).** Moving the derivation into core was cheap: it only ever
   needed a `SqlDriver` plus core's `extractRefs`/`canonicalRefName`/`aliasKeysOf`. One copy of the
   derivation AND of the reads (`backlinkRows`, `linkGraph`), so device and server cannot disagree.

How the replica keeps it current: **dirty-queue triggers + drain before read**, not per-call-site
hooks. The replica's state changes along paths that are not `applyOps` (snapshot bootstrap inserts
raw rows, `refused-page.ts` hard-deletes), so SQL triggers on `block`/`block_prop`/`page`/
`page_prop` record every touched id in `ref_dirty` whatever wrote it, and `drainRefIndex` re-derives
those (`reindexRefs`) before `pageBacklinks`/`graphLinks` read. Typing pays one guarded INSERT per
write; derivation runs when references are read (the panel is under every page, so right after the
coalesced write, off the keystroke path). `kind='text'` vs `'block'` separates in-place edits from
moves/creates/deletes so `reindexRefs`'s new `samePlace` option can skip the subtree walk when a
block's link set did not change.

Local-first rule (`data/local-first.ts`): the device's answer, always; the server only if the
replica could not build the index (SQLite without what it needs) and there is a server. No server
second-guessing: once the replica holds the graph there is no "real reason". Before bootstrap
completes the panel is empty; `onBootstrap` invalidates every table, so it refills.

Migration of an existing replica: `ensureClientRefIndex` (every open, `IF NOT EXISTS`, one
savepoint, never fatal) creates the tables and triggers; a replica that already had pages gets one
`('all','*')` row, so its first drain does `rebuildRefIndex` — a new in-memory full rebuild in core
(path = parent's path + own refs, memoised; page ids resolved in one final `reresolveIndexTargets`).
A drain with more than 2,000 dirty blocks (bootstrap, a long pull) also takes the full path.

Costs:
- No foreign keys on the replica's index tables (the server's have them). Found by e2e: with
  `foreign_keys = ON` the refused-page hard DELETE failed and lost an offline page.
- `syncVersion` no longer re-reads references (B-83's reason is gone: the answer does not depend on
  what the server has seen; server-minted pages arrive as pulled ops that bump the tables anyway).
- "Link all" is a server op; not offered at all with no server (local-only). Offline with a server
  it still tries and reports the failure (logged below).

## Measured (`tools/probes/client-ref-index-cost.ts`, sqlite-wasm 3.53.4 in Node, in-memory VFS;
owner-shaped graph `~/notes-graph` imported read-only: 1,211 pages, 18,628
blocks, 1,188 block props, 43 page props). The machine was shared with other agents; numbers varied
~2x between runs, ranges given.

- One-time migration (first drain, full rebuild): **0.69–1.9 s** (per-block derivation before the
  in-memory rebuild: 2.8 s). Phone CPU will be slower; not measured on a phone.
- Bootstrap drain (all 19.8k rows dirty → full): 0.70–1.8 s. Insert overhead of the dirty triggers on
  a bootstrap: not separable from run-to-run noise (FTS-only 1.5–3.7 s vs with triggers 1.4–3.6 s).
- Edit a leaf, drain: 2 ms. Edit the root of the biggest subtree (961 blocks) adding a link:
  0.16–0.49 s (the server does the same walk per write). Same root, edit without changing links:
  **0 ms** (the `samePlace` shortcut).
- Reads: `backlinkRows` with unlinked, busiest pages: 22 ms (1,092 linked), 60–67 ms ("Task",
  1,074 linked + 46 mentions).
- **Parity**: replica's tables vs the server's own for the same graph, row for row: `ref` 2,185/2,185,
  `path_ref` 32,671/32,671, `page_tag` 827/827, `page_alias` 3/3 — zero rows only on one side.
