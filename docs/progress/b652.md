## The fix, in one paragraph

An accepted `block.text` moves from `pending_op` to `sent_text` (with its server `seq`) instead of
vanishing; a pull drops it when the op comes back or the cursor passes its `seq`. Detection walks
the pulled batch in `seq` order and compares each foreign `block.text` against this device's
unseen text (pending + sent rows newer than the newest own op seen so far in the batch). Merge base
is the OLDEST unseen row's base; merge ops keep that base; an in-batch merge stays "mine"; and
`mergeBase` falls back to a verifiably-contained ancestor (author's previous text, or a text the
incoming op contains whose author's latest `mine` already holds) before declaring a conflict.

## Decisions / rejected

- Server-side detection: can only see the "incoming op loses LWW" half without a protocol change
  (block.text carries no parent); needs a wire field old clients don't send; two detectors racing.
- Pull-before-push on reconnect: doesn't fix two online devices that each push before pulling.
- Acked flag in `pending_op`: every outbox reader would need to skip them.

## Found in passing (all fixed here)

1 was reproduced on `59aa77b` by its own test (pull first, so not B-652 itself). 2 was seen in a
random-schedule trace during this work; on `59aa77b` it is there by code reading
(`enqueueForPush` wrote `base` NULL, `resolveTextConflicts` skipped a NULL base), not separately
reproduced. 3 measured on `59aa77b`.

1. **Merge base taken from the newest pending row** silently reverted an earlier local edit: two
   offline edits "one two three" → "ONE two three" → "ONE two THREE", other device "one TWO three"
   → merged "one TWO THREE" (ONE lost). Test: "two local edits of one block before the other
   device's edit arrives: the merge keeps the first one too".
2. **Merge op queued with `base = NULL`** made the next foreign edit skip detection and win by LWW
   over the merge (lost a third device's word). Tests: "three devices edit different words
   offline … one text with all three edits" (3 orders), random merge mode.
3. **B-642 e2e test flaky** ("one device offline: it comes back…"): 6/20 failures on `59aa77b`,
   both edits in one millisecond, HLC tie decided by random device id. Fixed by giving B a clock
   1 s ahead. Now 20/20.
4. Spurious conflict copies for clean multi-device merges (a merge op carrying a stale word):
   477/2000 random merge-mode runs → 0/2000 with `mergeBase`'s candidates. Probe:
   `tools/probes/b652-merge-base.ts` (why a third device's newer text is NOT a safe base).
