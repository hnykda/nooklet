# B-587 progress (HLC order vs seq order on a name collision)

Branch: `worktree-agent-aea25230c5fee842c` (reset to main `c897962` first). Not merged into main.

## Question settled: it IS a convergence bug, not only a verify false alarm

Deterministic test `apps/web/src/sync/e2e.test.ts` "a page created under a name the server freed,
with an HLC older than the freeing op, converges on every replica (B-587)": real server, real
`SyncClient`s. A's clock runs 5 s behind (deterministic stand-in for "same millisecond, before A
heard of seq 5"; ADR 003 only rejects clocks running *ahead*), so A's `page.create` HLC < the
server's `refpages` `page.delete` HLC, and it lands at a later seq. Result on `c897962`:
`expected [ 'C', 'D' ] to deeply equal []` — C (bootstrapped before, then one incremental pull of
delete + A's ops) and D (one pull of the whole log) both lack A's page and block. A, B (live, one
push response / pull at a time) and E (snapshot afterwards) match the server. `verifyRebuildParity`
also diverges (the probe `tools/probes/b587-hlc-order-name-collision.ts` shows it).

Cause: `SyncClient.pull()` and `verify` hand a server-log batch to core `applyOps`, which re-sorts
it by HLC; a collision check then meets state the server never showed that op.

## Fix (ADR 026)

Batches read out of the server's op log are applied in `seq` order, as given:
`applyOps(driver, ops, { order: "seq" })` (new `ApplyOpsOptions`, default stays `"hlc"`). Used by
`SyncClient.pull()`, `SyncClient.applyPushResponse()` (corrections) and `verifyRebuildParity`.
This is what `docs/spec/sql-schema.md` rule 26 already said ("replaying in `seq` order").

Rejected: server re-stamps/rejects an op whose HLC is behind ops it applied on the same name — see
ADR 026 for costs.
