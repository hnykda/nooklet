# B-640: a block's text invisible until opened for editing

**State:** fixed on this branch, verified (2026-10-04). Not merged to main.

## Cause (with evidence)

The data was never wrong. Block `1m431z65as6tgd` ("Ok these ones are added on mobile in airplane mode")
in a backup of `~/nooklet-test` is an ordinary row: plain one-line content, no properties, not
collapsed, three live children, parent "Three" at `a2` (moved there at 09:07 by op 63; it was top
level at `a3` when the owner reported it). The Mac app's own replica (a read-only copy of its OPFS
SAH-pool file, header stripped) holds the same rows. The op log has nothing unusual: the Mac's
Enter created it empty (op 19), Shift+Tab moved it to top level (22), and the phone typed into it
online (23, 25). Only "Nothing"'s text conflicted later (`conflict_copy`, ops 41/42). A fresh
Chromium or WebKit load of the page renders it correctly.

It is a **WebKit rendering bug triggered by `content-visibility: auto` on `.vr-row`** (`editor.css`,
the long-page strategy). Suppose a `content-visibility: auto` element is inserted with focus moving
into it. WebKit then leaves it *skipped*, so it is never painted. That holds even while the element
is on screen, after focus has left. Enter does exactly this: it inserts a new row and moves the
single editor into it in the same task. When the next Enter (or Escape/click) moves the editor on,
the row shows nothing, not even its bullet, while its children render normally. Clicking the row
re-enters edit mode and shows the text and the editing row's collapse arrow.

- `tools/probes/b640/webkit-cv-focus.mjs`: plain DOM, no app. In WebKit the rows the editor moved
  through report `checkVisibility({contentVisibilityAuto:true}) === false`, and a screenshot shows
  them blank. Chromium renders them. With `content-visibility: visible` the rows render, and they
  also render when the row that holds the editor is exempt.
- `tools/probes/b640/one-device.mjs`: in the real app, `- a`, End, Enter, `b`, Enter leaves "b"
  skipped in WebKit. The pre-existing row "a" is fine. Only rows created by Enter are affected.
- `tools/probes/b640/two-devices.mjs` replays the owner's session with two WebKit contexts, the
  phone going offline. It reproduced the screenshot exactly: "Ok these…" and "well and here…" blank
  on the "Mac", and "There is this"/"And that" blank on the "phone". It is clean with `NOCV=1`, clean
  in Chromium, and clean after the fix.
- `row-mutations.mjs` logs the DOM sequence the app performs on Enter, which is what the plain-DOM
  probe copies.
- Probes that came up negative and were kept as a record: `stress.mjs` (40 random remote
  moves/inserts/edits, no skipped rows), `scenarios.mjs`, `live-move.mjs` and `sim-remote.mjs`
  (remote-only edits in the iOS 27 Simulator's Safari, no repro). Remote changes alone do not
  trigger it. A row created here with Enter does.

## Fix

`apps/web/src/editor/editor.css`: `.vr-row-editing { content-visibility: visible; }`. A row is
therefore only `auto` after the editor has left it, a case WebKit handles. Long pages keep the
optimisation for every row but the one being edited.

  `biome check . --diagnostic-level=error`: clean.
- There is no unit test: jsdom has no rendering, and the bug lives only in the engine.

## Still unverified

- Not run on a real iPhone or in the real Mac app (WKWebView). Playwright's WebKit build and iOS 27
  Simulator Safari are the stand-ins. The Simulator was only driven with remote edits (no repro
  there, consistent with the cause), because without a GUI I could not type into it.
- Other ways focus can enter a row as it is inserted, besides the editor (e.g. a focused
  `.vr-block-view` in block-selection mode on a freshly inserted row), are not exempted. None was
  observed.
