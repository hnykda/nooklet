# B-660: `SQLITE_CONSTRAINT_FOREIGNKEY` on `INSERT OR REPLACE INTO block` in the replica

Branch: `worktree-agent-a36a967bfd0a09cab` (based on `385a139`). Status: fixed, e2e run pending at
time of writing (see "Verification").

## Cause (with evidence)

- **Code path:** `SyncClient.bootstrap()` (`apps/web/src/sync/sync-client.ts`), the snapshot apply.
  It is the only `INSERT OR REPLACE INTO block(` in the client.
- **Which FK:** `block.parent_id REFERENCES block(id)`. The replica runs with
  `PRAGMA foreign_keys = ON` (`apps/web/src/db/sqlite-wasm-driver.ts`), checked per statement.
- **Order that triggers it:** `/sync/snapshot` returns `SELECT * FROM block`
  (`packages/server/src/sync/snapshot.ts`), which is rowid order, i.e. creation order. A block
  moved under a block created after it is listed before its parent, and its insert fails.
  Enter in the editor (split, then indent) or any `block.move` produces this shape, so any
  graph that has been edited a little hits it. The b640 agent's server had been through its
  move/indent probes, which is why a "fresh page" showed it there; on an untouched server
  `row-mutations.mjs` does not reproduce it (checked).
- **Repro:** `tools/probes/b660/snapshot-fk.mjs`. Before the fix it logged the error in WebKit
  **and in Chromium** (Chromium with OPFS, WebKit on the in-memory fallback). Not WebKit-specific.
- **`INSERT OR REPLACE` delete-then-insert:** not the cause. Immediate FK checks run at the end of
  the statement, by which time the replaced parent row is back. Covered by a test anyway
  (re-bootstrap over a replica holding the rows).

## Was data lost?

The failing insert threw inside `driver.transaction`, so the **whole bootstrap rolled back**: no
pages, no blocks, cursor still 0, replica not marked bootstrapped. `worker-core.ts#start` swallows
that and pulls the op log from cursor 0, which rebuilt everything — so on a server whose op log is
complete, nothing was lost. Cost: a full op-log replay on first load, and since the bootstrap
flag never got set, every later cold start downloaded the snapshot again and failed again (the
pull after it is incremental from the stored cursor; this part is from reading the code, not
measured).

But once `nooklet gc` has trimmed the op log (`DELETE FROM op WHERE seq < floor`, `gc.ts`), the
fallback cannot rebuild what was trimmed: **a new device came up missing every page/block whose
ops were collected**. Shown both ways:
- unit: `apps/web/src/sync/e2e.test.ts` "a fresh replica gets every row even after the server's op
  log was trimmed" — red before: replica empty vs server's page + 2 blocks.
- browser: `TRIM=<graph.sqlite> ENGINE=chromium node snapshot-fk.mjs <base>` on the pre-fix build
  rendered **no rows**; after the fix, `newer | older` in Chromium and WebKit.

## Fix

`PRAGMA defer_foreign_keys = ON` as the first statement of the bootstrap transaction: FKs are
checked at COMMIT, so row order inside the snapshot no longer matters, but a snapshot that is
inconsistent as a whole is still refused. SQLite resets the pragma when the transaction ends.
Client-side rather than sorting on the server, so it holds against older servers too. Server
untouched.

## Tests (red before, green after)

`apps/web/src/sync/e2e.test.ts`, describe "a block moved under a block created after it (B-660)"
(real `SyncClient` against the real in-process server, `dumpState` replica-vs-server):
1. bootstraps a fresh replica whose snapshot lists the child before its parent — red:
   `FOREIGN KEY constraint failed`
2. a fresh replica gets every row even after the server's op log was trimmed — red: empty replica
3. re-bootstrapping over a replica that already holds the rows replaces them cleanly — red
   (first bootstrap failed); guards the REPLACE path
